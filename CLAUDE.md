# deephaven-questdb

Real-time crypto analytics stack. Cryptofeed streams trades and orderbooks (Coinbase, Bitstamp, Kraken; BTC/ETH/AVAX/SOL-USD) into QuestDB. Deephaven reads QuestDB as static snapshots and as live ticking tables.

## Architecture

```
Exchanges -> cryptofeed -> QWP/WebSocket (questdb:9000) -> QuestDB 10.0.1 (WAL tables)
          -> Postgres wire (questdb:8812, admin/quest) -> Deephaven server-ui 42.6 (UI :10000)
```

- `docker-compose.yml`: services `deephaven` (-Xmx12g, anonymous auth), `questdb`, `cryptofeed` on network `quest_ntw`. Deephaven and cryptofeed wait for QuestDB's healthcheck. QuestDB sets `QDB_CAIRO_WRITER_DATA_APPEND_PAGE_SIZE=1M` (the 16M default preallocated ~700 MB for a few thousand rows of a 42-column table).
- `./data/deephaven` is mounted at `/data/storage`; notebooks are at `/data/storage/notebooks` (on PYTHONPATH). `./data/questdb` is QuestDB data (gitignored).
- Schema (`docker/cryptofeed/src/init_questdb_tables.py`):
  - `trades`: TIMESTAMP_NS, SYMBOL cols, `price`, `size`, `trade_id`; PARTITION BY HOUR, WAL (hourly like every table and view here: DAY partitions made each small out-of-order commit rewrite a long stretch of a day, ~20,000x write amplification on `trades`; HOUR measured ~23x).
  - `orderbooks`: `bids`/`asks` as `DOUBLE[][]` ([[prices],[sizes]]); PARTITION BY HOUR, WAL, TTL 1 HOURS (QuestDB's minimum TTL unit is HOUR and TTL must be a multiple of the partition size; the view `orderbooks_1s` keeps the downsampled history). An existing DAY-partitioned table must be dropped (with `orderbooks_1s`) and recreated; stop cryptofeed first or ingest auto-creates it with defaults.
  - Materialized views: `orderbooks_1s` (SAMPLE BY 1s); `perps_liquidity_1m`, `perps_trades_10s`, `spot_trades_10s` (see Gotchas). `perps_liquidity` is a table (TTL 3 DAYS).

## Key files

- `Makefile`: build, build_with_drop, up, down, rebuild, restart, clean, ps, logs*, test, pytest, urls, format, lock-cryptofeed, lock-deephaven. There is no `start` target: `make build && make up` (or `make rebuild`).
- `pyproject.toml`: optional dep groups `cryptofeed`, `deephaven`. Ruff: line length 100, py312 (Deephaven's Python; cryptofeed runs 3.13), double quotes. Pytest testpaths: `docker/cryptofeed/tests`.
- `docker/cryptofeed/Dockerfile`: python:3.13 (cryptofeed 3.x requires it); overwrites cryptofeed's `exchanges/coinbase.py` with `src/coinbase.py`, the no-auth hack: it keeps using the public Coinbase Exchange feed (`wss://ws-feed.exchange.coinbase.com`: `matches`, `level2_batch`, `ticker`) instead of upstream's Advanced Trade client. It is ported to cryptofeed 3.0.1 and the build fails if another version is installed; on a cryptofeed upgrade re-port it (diff against the new upstream `coinbase.py`).
- `docker/cryptofeed/src/script/cryptofeed_0_startup.sh`: init tables, sleep 2s, launch the trades, orderbooks and perps feeds, restart on death.
- `src/questdb_writer.py`: `QuestDBWriter` (questdb SDK; QWP over WebSocket by default, `protocol="http"`/`QUESTDB_PROTOCOL=http` for ILP/HTTP). Rows are appended per tick and published by a 25 ms background flush: row() never blocks, rows are visible ~20-70 ms after the tick (ILP/HTTP defaults: ~560 ms median) and a multi-second server outage is buffered and replayed without loss. Server rejections arrive asynchronously (`writer.rejections`, logged); do not call `flush(wait=True)` per tick (~10 ms each). `write_trade`, `write_orderbook` (2D numpy), `execute_sql` (REST).
- `docker/deephaven/Dockerfile`: pip installs questdb, connectorx, sqlalchemy, psycopg2 and `deephaven-plugin-tradingview-lightweight==0.0.1` (TradingView charts; alpha); exact versions in `docker/deephaven/constraints.txt`. The old `TableDataService` callback patch was removed (fixed upstream in 42.6).
- `data/deephaven/notebooks/qdb.py`: static access, over QWP by default (`run_query(sql)` -> Arrow via `qdb_qwp.QwpReader`, nested arrays typed `double[][]`; 34 ms vs 74 ms for 5,000 trade rows) with ConnectorX over the Postgres wire as `transport="pg"` / `qdb.DEFAULT_TRANSPORT = "pg"`. `run_query`, `to_table()` (timestamp[us] -> timestamp[ns, tz=UTC], large_list -> list), `get_trades`, `get_candles`, `get_orderbooks`, `get_engine()` (SQLAlchemy, for live).
- `data/deephaven/notebooks/qdb_qwp.py`: `QwpReader`, reads over QuestDB's WebSocket protocol (QWP) as Arrow (nanosecond timestamps, no per-row Python conversion); used by `qdb_backend` (default transport) and `qdb_feed`. QWP cannot push, so readers poll. `DOUBLE[][]` columns arrive as real `double[][]` (usable in formulas, e.g. `bids[0][0]`): `TableDataService` infers `double[]` from a nested-list schema, so `qdb_qwp.schema()` reads the true dimensions from `table_columns()` and adds a `deephaven:type="double[][]"` field hint (a zero-row QWP result cannot tell `DOUBLE[]` from `DOUBLE[][]`). `QwpReader(flatten_arrays=True)` gives JSON strings instead. `create_live_table(..., transport="pg")` (or `TRANSPORT = "pg"` before running a live notebook) reads over the Postgres wire instead: microsecond timestamps, arrays as strings.
- `notebooks/qdb_backend.py` + `qdb_prefix.py` + `qdb_pagecache.py`: `QuestDBBackend(TableDataServiceBackend)`, the TableDataService live table over QuestDB storage (see Gotchas). One backend per table in a module-global registry (re-runnable notebooks; a re-run keeps the backend and its positions). Polls every 50 ms with interval `count()`s. API: `create_live_table(name, transport="qwp", settle_seconds=3.0, history_seconds=None, ...)`, `get_backend(name)` (`.prefix.size/.watermark/.late_rows/.missing_rows`), `set_verbose`, `stop_monitoring`. `qdb_prefix` is pure logic, tested in `tests/unit/test_prefix.py`.
- Notebooks: static `trades_static.py` (binds `trades_static`), `orderbooks_static.py` (binds `orderbooks_static`); live notebooks bind `trades` / `orderbooks`; live `trades_live_via_questdb_wal.py`, `orderbooks_live_via_questdb_wal.py` (add `latency_seconds`); charts `trades_chart_live.py` (TradingView candles + volume, tick lines; `tvl` plugin 0.0.1 has no `tvl.legend`; candles are binned with `agg_by`, because plugin `auto_bin` produced a 0-based price axis), `trades_chart_simple.py`; dashboard `perps_dashboard.py` (see Gotchas).
- `docs/` status, orderbooks, bug report, `history/`; `docker/cryptofeed/tests/` unit/integration/simulation + `utils/` (status scripts) + `run_tests.sh`.

## How to run

- First run: `make rebuild`, wait ~30s, `make test`. Deephaven http://localhost:10000, QuestDB http://localhost:9000.
- Wrong timestamp type on tables: `make build_with_drop`.
- Format: `make format` (`uvx ruff format`). Tests: pytest via uvx.

## Gotchas

- **DH editor overwrites files**: closing a notebook in the Deephaven UI writes its (possibly stale) editor buffer back to `data/deephaven/notebooks/`. Close files in the UI before editing them from outside, and re-check `git diff` afterwards.
- **Tests are isolated**: `docker/cryptofeed/tests` write to throwaway `test_*` tables (dropped on teardown), never to live `trades` / `orderbooks`. Run with `make pytest`.

- **Timestamp precision**: tables must be TIMESTAMP_NS. If ingest writes beat the DDL, QuestDB auto-creates microsecond tables (fixed in 7b0bf73 with IF NOT EXISTS, 2s sleep, schema check). Deephaven rejects MICROSECOND units, so static loads must go through `qdb.to_table()`.
- **Two connection paths**: static notebooks use QWP (or ConnectorX with `transport="pg"`; `get_connection()` returns its string); live notebooks use SQLAlchemy via `get_engine()`. Mixing them gives `'str' has no attribute 'connect'`.
- **Column naming**: cryptofeed's `amount` is stored as `size`.
- **Perpetual futures** (`src/perps.py`, `src/script/cryptofeed_3_perps.py`, a third supervised process): BTC and ETH perps, linear (`BTC-USDT-PERP`, `BTC-USDC-PERP`) and inverse (`BTC-USD-PERP`), from Deribit, OKX, Hyperliquid, Binance (`BINANCE_FUTURES`, USDT-M only; COIN-M and USDC perps are deliberately not subscribed) and Bybit. They share the spot `trades` / `orderbooks` tables. `size` is always base coin; `trades` also has `size_native` + `size_unit` (BASE / USD / CONTRACTS), `contract_size` (1 for spot; coin or USD per contract), `contract_type` (spot / linear / inverse) and `notional_usd`, so `SUM(notional_usd)` is valid across every row. Inverse size = USD notional / price. Venues differ: Deribit inverse is USD, OKX is contracts (`ctVal` read from its instrument list), Bybit inverse is USD, Binance USDT-M is base coin.
- **Liquidity metrics** (`perps_liquidity`, one row per instrument per ~1 s, TTL 3 days; view `perps_liquidity_1m`): computed at ingest from the *whole* in-memory book (`perps.compute_liquidity`), because the stored `orderbooks` top-20 reach only 0.4-4.7 bps from mid. Columns: mid, best_bid/ask, spread_bps, bid/ask_levels, `bid_reach_bps` / `ask_reach_bps` (coverage), `bid_usd_{1,2,3,5,10,25,50,100}bp` / `ask_usd_...` (USD resting within N bps of mid, cumulative), `buy/sell_slip_bps_{10k,50k,100k,250k,500k,1m,5m}` (market order walk vs mid; NULL = the published book cannot fill it). Venues publish different amounts: Deribit the whole book, OKX 400 levels per side (reach ~6 bps BTC-USDT, ~18 BTC-USD, ~16 ETH-USDT, ~40 ETH-USD), Hyperliquid 20 levels (~2.4 bps BTC) at only ~10 updates/min. A bucket wider than a venue's reach is a lower bound: always compare against `*_reach_bps`. The cryptofeed numpy values must be plain Python floats before they reach the SDK (it rejects `numpy.float64`).
- **Hyperliquid** is stored as `BTC-USDC-PERP` / `ETH-USDC-PERP` (cryptofeed names them `-USD-PERP`, which elsewhere means inverse; `Venue.aliases` maps the stored symbol, and its size spec is base coin, not inferred from the suffix).
- **Binance is region restricted, Bybit is streamed over WebSocket only**: from this host `fapi/dapi.binance.com` REST returns HTTP 451 and `api.bybit.com` REST 403, but the venues' WebSocket hosts are reachable. Bybit therefore runs through `src/bybit_ws.py`, a cryptofeed `Bybit` subclass (like the Coinbase hack, guarded by the cryptofeed pin) that lists BTC/ETH perps statically instead of calling REST and subscribes to `orderbook.1000` (1000 levels per side; cryptofeed hard-codes 200). Verified live: inverse sizes are USD contracts, `notional_usd == size*price` on every row, reach ~22 bps BTC-USDT / ~180 bps BTC-USD. Binance `fstream` WebSocket also connects, but its full book needs a REST snapshot (451), so Binance stays skipped until trades-only or a 20-level partial book is added. The perps process probes every venue at start, skips unreachable ones with the reason in the log, and re-probes every `PERP_REPROBE_SECONDS` (600). `PERP_VENUES=deribit,okx` restricts the set (names: deribit, okx, binance_futures, bybit, hyperliquid). Hyperliquid's raw 20-level book is extended with its WebSocket `nSigFigs=4/3` aggregated books (`perps.DeepBooks`, reach ~230 bps BTC, bucket-edge approximation); OKX is already at its 400-level WebSocket maximum.
- **Backfilling the contract columns** after adding them to an old `trades` table (one time): `UPDATE trades SET size_native = size, size_unit = 'BASE', contract_size = 1.0, contract_type = 'spot', notional_usd = price * size WHERE contract_size IS NULL`.
- **trades is deduplicated** (`DEDUP UPSERT KEYS(timestamp, exchange, symbol, trade_id)`, set by `init_questdb_tables.py`): a replayed trade (Coinbase re-sends `last_match` on every subscribe; restarts; QWP reconnect replay) overwrites itself. `trade_id` must stay in the key (thousands of timestamps hold several distinct trades) and must never be NULL: NULL ids collapse distinct trades, so the writer substitutes a unique `rx-...` id. Rows stored before DEDUP was enabled are not rewritten. Stored timestamps are `TIMESTAMP_NS` but the sources only give microseconds; sub-microsecond digits are float rounding noise.
- **Perps dashboard**: `notebooks/perps_dashboard.py` (+ `perps_dash_lib.py`, tested in `tests/unit/test_perps_dash_lib.py`), widget `perps_dashboard`, run with `exec(open('/data/storage/notebooks/perps_dashboard.py').read())` (~12 s, re-runnable; derived tables live in `pd_scope`). Deribit vs other venues: depth/slippage matrices, prices & basis, volume & flow. All compute is in QuestDB views, polled by `qdb_feed.feed_query` (~2k rows in Deephaven, no raw ticks). deephaven.ui quirks: memoized components with event handlers stop responding to clicks; `use_table_data` keeps its first table, so key components by selection.
- **QuestDB CPU**: with defaults QuestDB held ~6.6 of 12 cores for ~300 rows/s (load average 24-28): 12-thread network/write/query pools spinning on ~140 tiny WAL commits/s (25 ms client flush, one commit per flush, plus a refresh per materialized view), ~900 INFO log lines/s, and 20,000x write amplification on `trades` (DAY partition, DEDUP, out-of-order exchange timestamps; `tables()` has `wal_tx_size_*` / `table_write_amp_*`). Now: pools sized 2/4/4, WAL apply 2, MV refresh 1, query-progress and INFO logging off (docker-compose env), and cryptofeed flushes every `QUESTDB_AUTO_FLUSH_MS=250` instead of 25 (rows visible ~300 ms instead of ~70 ms). Measured ~6.6 -> ~2.2 cores. All tables and views are now PARTITION BY HOUR (write amplification on `trades` 20,000x -> ~23x; QuestDB ~1.8 cores). `orderbooks_1s` has no TTL, so it adds 24 partitions a day.
- **QuestDB disk**: `QDB_CAIRO_WRITER_DATA_APPEND_PAGE_SIZE=1M` (docker-compose) shrinks the per-column preallocation from the 16M default; with ~42-column tables and a few thousand rows per partition that was the bulk of the disk (3.3G -> 0.8G measured, nothing else changed). Existing partitions shrink only as they are rewritten/rolled over by TTL. Parquet/ZSTD conversion is possible for old non-view partitions but is not enabled.
- **TableDataService live tables are exact, ~4 s behind**: TDS addresses rows by position, fetches each column lazily at different moments, re-reads pages it dropped (soft-referenced) and ignores a size that shrinks. QuestDB orders rows by their (exchange) timestamp, so with plain `ORDER BY timestamp LIMIT lo,hi` paging a late row shifted every later position and 1.0% of tail rows had columns from different rows (e.g. a BTC perp at an AVAX price; a 5 s page cache did not fix it). `qdb_backend` therefore exposes only a settled prefix (`qdb_prefix`): rows with `start <= timestamp < W`, `W = min(max(timestamp), now) - settle_seconds`, never decreasing, ordered by timestamp + DEDUP upsert keys + every other column (rows tying on all scalar columns, e.g. Kraken books sharing a timestamp, are ordered client side by their array bytes: sorting by `cast(bids as varchar)` in SQL made pages ~5x slower), cut into ~1 s segments whose row counts are frozen when published. A page is one range query trimmed to those counts, so positions below the published size never move; `qdb_pagecache.get_range` serves every column of a page (Deephaven fills each column from its own length) from that one load. Cost: a 32k-row orderbooks page ~0.4-0.5 s, a 64k trades page well under that. Measured lateness (15 min, all live feeds, row timestamp vs max(timestamp) when it became visible): trades p99 0.52 s, p99.9 1.0 s, max 2.05 s (Coinbase), 3 of 19,953 rows > 2 s, 0 > 3 s; orderbooks max 0.87 s. Default `settle_seconds=3.0`: the newest row of a live `trades` table is 3.4-5.1 s old (median 4.0 s, `latency_seconds`; settle + poll + Deephaven's 1 s update cycle). Verified live against QuestDB (6 min, 58,800 tail rows fetched while rows arrived, some columns first and the rest a second later; 260,190-row final table; both transports): 0 rows not in QuestDB, 0 with `notional_usd != size * price`, every position identical to QuestDB's ordered prefix, 10-min window 16,678 rows / $68,742,260.83 identical. The old backend on the same data: 1.02% of tail rows not in QuestDB (380 of 37,200; 138 with `notional_usd != size * price`). Orderbooks (`double[][]`, 24,900 tail rows, 104,349-row table): 0 bad, same key sequence and rows as QuestDB (old: 0.87% of tail rows). 0 late rows across a cryptofeed container restart (~1 min stall, then replay). Residual risk: a row later than `settle_seconds` is left out (counted in `get_backend(name).prefix.late_rows`, logged) and a published row that disappears (TTL dropping its partition: orderbooks keeps only 1-2 h, so the head of a long-running orderbooks table, or a DELETE) is served as a null row if Deephaven re-reads it (`missing_rows`); either affects only its own ~1 s segment. `history_seconds` bounds how far back a table starts; the orderbooks notebook uses 900 s (measured: a whole-table orderbooks backend lost 385,052 published rows to the hourly TTL drop within the hour).
- **`qdb_feed` for dashboards and views**: `notebooks/qdb_feed.py` polls QuestDB and publishes each row once through a table publisher: `feed_table(name, history_seconds, capacity=100_000, where=...)` for raw rows (a bounded `ring_table` by default; `capacity=None` opts into unbounded append-only; rows appear within ~0.25 s and late rows are appended, not left out), and `feed_query(sql, key_columns, ...)` for the current result of any SQL (a view, `LATEST ON`, a rolling aggregate), publishing only rows whose values changed and keeping one row per key. Materialized views rewrite their open bucket, so they cannot be read through the append-only TDS backend; use `feed_query`. Verified live: 1,276 rows / $3,997,671 identical to QuestDB for a fixed window, 0 inconsistent rows, 0 duplicates. Compute belongs in QuestDB views (`perps_trades_10s`, `perps_liquidity`, `perps_liquidity_1m`, `spot_trades_10s`, TTL 2-3 days); Deephaven should only hold small state tables.
